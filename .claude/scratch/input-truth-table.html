Reserved for navigation — same in every tool above

These gestures never reach the active tool. They pan, zoom, or rotate the canvas regardless of what's selected, and nothing above overrides them.

  • touch · 2-finger pan, pinch-zoom, and rotate together (the anchor-solve gesture)
  • mouse · middle-drag pan
  • mouse / trackpad · wheel zoom
  • touch · 1-finger nothing reserved — always goes to the active tool's Touch column above, see Q1

Open questions — before this gets built

  1. Is one-finger touch ever navigation?
    This table assumes no — a single finger always drives whatever the active tool's Touch column says, even if that's "no effect." Camera navigation becomes two-finger only. The alternative is a fallback rule ("pan only when the active tool has no touch action"), but that conflicts with Move/Transform/Text, where a finger must drag the object, not the camera.
    leaning: two-finger only
  2. "Finger can move layers" — panel, canvas, or both?
    The table currently gives touch both: reordering a row in the Layers panel, and dragging a layer's pixels on canvas with Move. The panel case needs its own disambiguation from list-scrolling — likely a brief press-and-hold before the drag starts, matching the standard iOS reorder gesture — since a plain one-finger drag on a scrollable list is otherwise ambiguous.
  3. Does long-press-to-sample work inside every tool, or only some?
    Treated here as a global modifier — available no matter which tool is active, the way Alt-click samples color on desktop regardless of tool. Confirm, or name the tools where it shouldn't fire.
  4. What does a denied touch input actually do?
    For a ✕ cell (Brush, Selection, Shape, …), should a one-finger drag be fully inert — no visual feedback at all — or should it show some cue (a cursor change, a brief tooltip) explaining why nothing happened?
  5. Is Pen identical to Mouse in every row?
    Assumed yes throughout — the Pencil is treated as a precision pointer with the same rights as a mouse everywhere. Say so if any row should actually differ for Pen specifically.
  6. Crop / Gradient / Frame-Slice: two phases, two rules?
    The table denies touch for *defining* a new crop rect, gradient drag, or frame — that's content-editing. But once one exists, dragging its handles falls under "On-canvas handles," where touch is allowed. Confirm that split is right, since it means these three tools behave differently depending on whether the shape already exists.
Where this sits today: mouse-vs-touch identity is resolved once per gesture from SDL's own device id, with finger-count only overriding it at 2+ fingers (the real two-finger reassignment case) — a one-finger mouse click was previously misread as touch because a click also registers as a phantom finger on iPadOS. Roughly 20 of the ~25 canvas interaction handlers don't yet check device identity at all; building this table means adding that check to each one, keyed off the rows above.
